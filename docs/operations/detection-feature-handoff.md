# Synthetic detection feature handoff

The existing automatic detection loop can receive an optional host-owned `DetectionFeatureReader`. Supply it as the fourth `DetectionRuntime` constructor argument or the third `createApp` argument. Default initialization retains its existing behavior. No HTTP body or environment path selects this reader.

For an explicitly prepared local no-cache feature store, `LMPS_DETECTION_FEATURE_CONTEXT=1` now connects the existing `LMPS_LOCAL_FEATURE_CONFIG` to the scheduler at API startup. Both authenticated feature and detection configuration are required. The reader uses the validated private store, accepts exactly one configured query for the target and uses the current clock for freshness. A required-cache configuration cannot fall back to filesystem evidence. This opt-in is forwarded by the local Core companion; it is disabled by the Intake viewing runner. There is no automatic inference of account context for the imported LMPS cohort.

For each eligible local synthetic target, the reader receives `(target, signal)` and returns `{publication, scope, serving_request}` within a fixed two-second deadline. It must honor cancellation and own its resources; a non-cooperating reader's external IO cannot be forcibly stopped by this callback contract. The handoff reads the approved policy and current immutable observation, uses `bindFeatureRiskRequest` to reconstruct only the validated P04 frozen history and passes that context through the existing approved-job transaction. That transaction independently checks active policy generation and pins the policy. The normal leased worker, idempotency and immutable assessment/Alert path are reused.

The P04 bridge checks namespace/target/revision, currency/window, source time, bounded event history, publication arithmetic and freshness. Missing/stale/partial evidence withholds context; a reader/configuration failure rolls back the enqueue and marks the runtime unavailable. User-supplied provenance never gains synthetic account context through this reader. Retries use the frozen job context; current cache reads cannot rewrite it.

Concurrent dispatchers acquire a transaction-scoped lock for the target revision and recheck for an existing job before reading features. Only the first dispatcher can freeze that revision's context; later dispatchers do not replace it with a newer cache observation.

The resulting assessment's `feature_snapshot_sha256` binds the frozen risk context, not the full original feature publication file. Independent publication/source-prefix provenance remains in the original feature evidence. This is an explicit extension point for accepted synthetic fixtures; no production reader or real-source attestation is configured here. Reference/model orchestration and their source/identity/governance approvals remain separate integrations.
