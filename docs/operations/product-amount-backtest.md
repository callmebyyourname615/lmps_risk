# Candidate LAK product amount screening

The user declared a 200,000,000 LAK per-transaction product cap and approved offline amount bands, independent success/refund facts and a full October backtest. This is a candidate analysis profile. It does not replace approved policy versions, normalize actual LMPS payments, establish product membership, create Assessments/Alerts or enforce payment decisions.

## Domain functions and boundaries

`declaredIntakeLifecycle` in `@lmps/contracts/intake-source-contract` adds mapping `operator_intake_independent_status_refund_v3`. Existing v1/v2 functions retain their behavior. V3 independently reports:

- Literal `OK`: `reported_success=succeeded`; other nonempty unpadded text: `not_successful`; NULL/empty/padded text: `unknown`. It never guesses failed versus pending and does not trim/case-fold into success.
- `shouldrevert` string `1`: `refund_instruction=required`; string `0`: `not_required`; other valid integer text/NULL: `unknown`. `OK` and required refund can coexist.
- A present originalreference differing from reference: `prior_reference_candidate`; identical references require review. Actual references are not returned. This identifies a declared DRS correction marker, not a proven unique business payment or complete reference chain.
- Refund completion, reversed amount, net executed amount, account/business-payment identity and known-at remain unverified/null. The declared clock fields are txtime (occurrence) and requesttime (request receipt), with timezone unresolved.

`classifyProductAmount` and frozen `LAK_PRODUCT_AMOUNT_PROFILE` are exported by `@lmps/risk`. Decimal strings become exact BigInt cents; no floating-point money is used.

| Band | Recorded LAK amount |
| --- | --- |
| below_review | `0 < amount < 20,000,000.00` |
| review | `20,000,000.00 <= amount < 100,000,000.00` |
| high | `100,000,000.00 <= amount < 180,000,000.00` |
| near_cap | `180,000,000.00 <= amount <= 200,000,000.00` |
| above_cap | `amount > 200,000,000.00` |
| nonpositive_withheld | LAK amount zero or negative |
| currency_out_of_scope | Other currency; no LAK threshold is copied |

These are amount-band labels, not calibrated fraud severities/probabilities. The cap equality is included in near_cap. Above-cap observations remain visible as a separate review cohort; they are not silently discarded, automatically called fraud, or assumed to belong to this product. The amount's major/minor units and product membership still require evidence.

## Full-month command

After building the workspace's risk/contracts dependencies:

```sh
pnpm --silent dataset:amount-backtest \
  --plan /ABSOLUTE/PRIVATE/readiness-plan.json \
  --profile /ABSOLUTE/PRIVATE/MONTH-READINESS/v1/ANALYSIS-ID/report.json \
  --output "$PWD/.local/product-amount-backtest"
```

The prior report must be an unchanged canonical 15-pattern month-readiness artifact whose directory ID, request hash, producer source binding and catalog match. One transfer table with the rich account/reference/refund projection is required. The verified profile must have zero malformed rows, invalid keys, duplicate source keys and conflicts. The tool reuses that exact-input uniqueness and field-validity evidence, validates all source file hashes/counts/headers again and reconciles physical/valid/out-of-month/invalid counts. A changed source or producer requires new profiling evidence. Content hashes are not independent source/execution attestation.

The Python streaming reducer receives the canonical TypeScript candidate profile and parity cases generated by the actual source/amount functions. It checks all cases before reading files; this includes exact cent boundaries, NULLs, unknown flags, non-LAK values and Unicode whitespace. Shared private readers retain their file/header/gzip/escaping/mutation limits. Input caps are 4,096 files, 30 million physical rows, 16 GiB compressed/decoded, 30 minutes and a 1 GiB free-space reserve. No database or source connection is opened. Temporary `.amount-backtest-*/progress.json` under the output parent contains only file/row counts and is removed on success or handled failure.

## Counts, traces and immutable publication

The report groups recorded amounts by disjoint band and reports success, refund instruction, their joint combinations and DRS markers independently. It also backtests `>=20m`, `>=50m`, `>=100m` and `>=180m`. Each threshold distinguishes all recorded matches from matches inside `(0,200m]`; status/refund counts apply to the latter. These thresholds overlap: their union is the lowest threshold's count, not their sum. Other-currency amounts are not summed together. Invalid rows and valid rows outside the requested requesttime month are withheld explicitly.

The scope is the received **current snapshot in a requesttime month**, not historical event-time replay. DRS in-place updates can remove prior states. txtime is retained as a literal and its outside-request-month count is reported; no UTC, known-at or complete business-payment history is manufactured.

Under `output/v1/<analysis-id>/`:

- `report.json`: candidate profile/mapping, aggregate bands/thresholds, input/profile/tool commitments, 15 core matched counts explicitly null/not_evaluated, parity and trace-verification receipts.
- `traces.json`: at most three largest examples for each band/success/refund/DRS group. These are bounded samples, not all candidates. They contain file/row pointers and hashes, literal times/amounts and derived facts; no account values, actual references, raw arbitrary status codes or source paths.

Before publication, amount bands are checked with the canonical TS function and every trace is independently replayed with the private source reader. Selected source files are fully rehashed and each row's source-key commitment, times, currency/amount and independent facts must match. Plan, prior report and source/compiled tool bindings are checked again. The existing exclusive immutable publisher writes both owned-private files. Exact retry returns duplicate; changed or partially published reports are never overwritten. Both accounts remain unresolved, including identical masks. Existing approved policies and frozen historical evidence retain their meaning.

## Verification and remaining work

Tests cover equality/below/above every amount boundary, large exact cents, OK+refund, unknown/NULL/invalid facts, unchanged v2 behavior, DRS markers, masking privacy, all threshold overlaps, non-LAK and over-cap exclusion, actual CLI/Python/TS parity, source mutation, private publication/replay, trace tampering, source-profile scope, resource limits and production refusal. Test fixtures are invented; actual monthly acceptance is recorded in `docs/implementation-status/current.md`.

Product selector/units, source authority, refund completion, stable pre-mask identity, correction/version/known-at history, timezone and authorized references remain open. Their absence is not an evaluated zero-risk result. Full 15-pattern detection and accuracy require eligible normalized observations, context, policies and reviewed labels; this command performs no operational assessment or enforcement.
