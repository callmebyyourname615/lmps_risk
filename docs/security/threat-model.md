# Local foundation threat model and abuse-test matrix

US-309 / P10-09-T1, 2026-10-26. This is a source-based model for the NestJS/TypeScript and Python/FastAPI local foundation. It is not a penetration test, security sign-off, release approval or closure of P10-09 or any target phase. No real attack or production validation was performed. `production_ready=false`; synthetic payment simulation remains `enforcement=false`.

## Evidence and trust boundaries

“Implemented” below means inspected source with an existing regression test, not that the test was executed for this task. All referenced suites await independent B03 host execution unless explicitly recorded in the appended [candidate handoff](../implementation-status/current.md). The B01 and B02 independent host acceptance sections in that file are historical receipts for their respective batches; they cannot establish B03 success. Private receipt outputs/hashes are host-owned and were not inspected outside this candidate. US-301–308 dependency completion must be established by durable host receipts, not inferred from source presence.

Assets are workspace-scoped Case/Alert/evidence metadata, audit history, private ingestion data, artifact and policy identities, synthetic payment binding/reservations, notification ownership/intent handles and immutable automation source/receipts. Actors include an unauthenticated caller, a legitimate user crossing workspace or assignee boundaries, a compromised scoped service, an insider with ordinary DB privileges, a privileged migrator/admin, an untrusted file/artifact producer and a candidate coding agent. Availability exhaustion, confidentiality disclosure, integrity substitution and replay are relevant across these boundaries.

| Boundary | Trusted input and untrusted crossing | Security limit |
| --- | --- | --- |
| Caller → API → Case storage | Local ES256 JWT principal supplies subject/workspace; bodies, identifiers and query filters are untrusted | Local synthetic identity is not corporate identity or proof of tenant onboarding. DB credentials and signing configuration remain trusted |
| Service → audit DB → operator | Ordinary roles are constrained by grants/triggers; privileged schema owner can change the enforcement mechanism | Append-only behavior for ordinary roles is not protection from superuser, backup replacement or host compromise |
| Source/file → private staging → publication/API | Source mapping, schema, bytes and claimed lineage are untrusted until validated | Full-account representation, masking boundary, stable account identity, source configuration and authority remain unverified; no account linkage inferred |
| Artifact producer → private loader → inference | Expected artifact digest, pinned packages and reviewed deserialization types constrain loading | A hash verifies bytes relative to its trusted expected value; it does not establish publisher identity or build provenance |
| Caller → synthetic payment simulation | Caller scope, exact money, parties, key and supplied clock bind local state | No real payment execution, bank balance, endpoint authority or distributed reservation guarantee |
| Intent → fake provider → deep link/detail | Ownership/version/idempotency contracts and opaque handles limit disclosure/replay | Provider acceptance is not device receipt/open/ack; detail retrieval still needs independent authentication and authorization |
| Agent candidate → verifier → publication | Exact reviewed scope, immutable source snapshots and independent verification separate implementation from acceptance | Candidate statements cannot grant approval or manufacture durable host receipts |

## Reading and extending the abuse matrix

The abuse-input column is an exercise specification, not a claim that every listed variation has a dedicated assertion. Linked test files establish only their implemented assertions; all execution outcomes for this batch remain subject to the host receipt. For example, `audit.test.mjs` explicitly tests ordinary-role rewrite/trigger denial and audit-failure rollback; `test_ml_serving.py` explicitly injects an unreviewed `os.system` serialization type. Neither establishes resistance to a privileged host administrator. The historical B01/B02 receipt sections linked above record their executed scopes only.

For each future exercise retain the matrix ID, exact source/toolchain revision, invented fixture identity, supplied clock, finite input/attempt cap, command, actual exit/result, expected versus observed denial and a redacted evidence digest. Verify both the response and unchanged protected state; a denial alone does not prove absence of side effects. Record failures and unavailable checks explicitly. Credential/PII canaries must be invented, and diagnostics must not reproduce actual secrets. Privileged-admin, corporate identity, real-source masking, publisher attestation, payment endpoint and device-delivery exercises are proposed owner-controlled work, with authorization and isolated fixtures still pending; they are not additional implementation in US-309.

## Pending defense decisions and verification handoff

Proposed owners above are roles requiring assignment, not commitments or accepted risk. Production identity/tenant isolation, privileged-admin tamper resistance, authoritative source/masking/identity, publisher provenance, real payment authority and authenticated push detail retrieval are unresolved defenses. Any owner-approved future exercise must name its authorized fixture, exact version, finite bounds, expected denial/no mutation/no disclosure and retained redacted evidence; failure stops the exercise. No missing defense is silently treated as implemented.

The independent verifier must execute all trusted automation tests and the frozen `full` group (`pnpm typecheck`, `pnpm test`, `pnpm build`, `pnpm verify:fresh`) using pinned toolchain identifiers from the reviewed manifest/runner, prepared offline caches and approved disposable host fixtures. It must also establish publication/secret scan, exact file/manifest-field scope, append-only status prefix, unchanged source/plan/Git/user material, B01/B02 history and all logins, plus dependency receipts and guarded promotion. No candidate login probes or credential reads are authorized. Online advisory audit is skipped under the offline contract, never passed by inference. Only the trusted verifier appends successful current-batch results and creates the durable receipt; documentation readiness closes no target phase.
